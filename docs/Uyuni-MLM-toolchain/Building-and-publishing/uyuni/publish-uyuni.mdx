# Publish Uyuni

Uyuni documentation is published to [uyuni-project.org](https://www.uyuni-project.org/uyuni-docs/). Build it with the same container and Task workflow as Multi-Linux Manager.

For setup, see [Container setup](../../Deployment-and-Installation/Use-our-doc-container.mdx).

---

## 1. Update config.yml

If not already updated during the packaging step, set the Uyuni fields in `config.yml` on your branch before you build.

Under `products.uyuni`:

| Field | What to set |
| --- | --- |
| `antora.title` | Antora component title, for example `Uyuni 2026.11` |

Under `products.uyuni.asciidoc.attributes`:

| Field | What to set |
| --- | --- |
| `releaseversion` / `productnumber` | Release label, quoted so it is kept as written (for example `"2026.11"`) |
| `productchartversion` | Helm chart version for this release |
| `gitchartsbranch` | Charts branch for this release |

Then review supported client versions in the shared `asciidoc:` block. Confirm the list and versions with the release managers and the product owner before you publish.

:::info AsciiDoc Attribute Software Versions
We will be automating these software version updates in the future. For now, check with release engineers or review the [SUSE Product End of Life / Lifecycle list](https://www.suse.com/lifecycle/) to see which versions we currently support.

You can also prompt an AI to quickly check supported versions against the following reference files in the Uyuni repository:
- [`mgr_bootstrap_data.py`](https://github.com/uyuni-project/uyuni/blob/master/susemanager/src/mgr_bootstrap_data.py)
- [`spacewalk-common-channels.ini`](https://github.com/uyuni-project/uyuni/blob/master/utils/spacewalk-common-channels.ini)
:::

## 2. Build

```bash
cd uyuni-docs
task container:build                 # once, or after Dockerfile.bci changes
task container:publish:uyuni
```

Limit languages or jobs if needed:

```bash
task container:publish:uyuni LANGUAGES=en
task container:publish:uyuni LANGUAGES="en ja" JOBS=4
```

Output lands in `build/` on the host.

---

## 3. Verify output

After the build completes, verify the generated documentation:

- **Check debug logs**: Review the build logs for missing AsciiDoc attributes, unresolved cross-references, or broken links. Correct any missing attributes in `config.yml` or the source files, then rebuild if required.
- **Review content and formatting**: Inspect major updates and newly added pages for formatting issues, table rendering defects, or glaring layout problems.
- **Inspect PDF output**: Check the generated PDF files in `build/` to ensure cover pages are intact, metadata/branding is correct, and there are no rendering errors or orphan elements across documents.

---

## 4. Deploy to gh-pages

Once verification is complete, deploy the build to the `gh-pages` branch:

1. **Back up the build to a temporary directory:**

   ```bash
   cp -r build/ /tmp/uyuni-build-temp/
   ```

2. **Check out the `gh-pages` branch and pull the latest changes:**

   ```bash
   git checkout gh-pages
   git pull origin gh-pages
   ```

3. **Create and check out a new feature branch:**

   Replace `YYYY.MM` with the target release (for example, `2026.11`):

   ```bash
   git checkout -b uyuni-YYYY.MM-ghpages-update
   ```

4. **Copy the build content from the temporary directory into your repository root:**

   ```bash
   cp -r /tmp/uyuni-build-temp/* .
   ```

   *(Ensure untracked build artifacts or translation folders like `build/`, `builds/`, and `translations/` are included in `.gitignore` if present).*

5. **Commit and push your changes to your feature branch upstream:**

   ```bash
   git add .
   git commit -m "Update Uyuni documentation for YYYY.MM release"
   git push -u origin uyuni-YYYY.MM-ghpages-update
   ```

6. **Create a Pull Request:**

   In the GitHub Web UI, open a pull request targeting the `gh-pages` base branch from your `uyuni-YYYY.MM-ghpages-update` branch.

7. **Notify Release Engineers:**

   Share the pull request link with the release engineers (RelEng) so they can review and coordinate the release.
